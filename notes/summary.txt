# Comprehensive Summary of Boiler Project Notes

## Migration & Architecture Evolution

### 3-Stage Pipeline System
The project underwent a major architectural refactoring from monolithic handlers to a clean 3-stage pipeline:

**Architecture:**
- **Stage 1: Detection** - Pattern matching to identify errors (ErrorClue objects)
- **Stage 2: Planning** - Convert clues into concrete repair plans (RepairPlan objects)
- **Stage 3: Execution** - Safely execute repairs with validation (RepairResult objects)

**Benefits Achieved:**
- Reduced handler complexity from 50-100 lines to 10-20 lines per component
- Each stage is independently testable
- Better validation prevents infinite loops
- Enables prioritization across different error types
- Clear separation of concerns

**Key Files:**
- `boiler/pipeline/models.py` - Core data structures
- `boiler/pipeline/pipeline.py` - Orchestration
- `boiler/pipeline/handlers.py` - Registration system

### Migration Progress
- **Migrated:** 8+ handlers from legacy system to pipeline
- **Remaining:** 65+ legacy handlers (still active as fallback)
- **Success Rate:** Achieved 86-100% pipeline success on test repos
- **Legacy Handler Tracking:** JSON debug output now tracks which legacy handlers are used, enabling data-driven migration prioritization

## C Error Handling (Critical Learnings)

### File Validation is Essential
**Problem:** Tools like `src_repair` were claiming success without actually modifying files, causing infinite loops.

**Solution:**
- Capture file hash before repair
- Verify hash changes after repair
- Return failure if no changes detected

### Distinguish Error Types
Not all undeclared symbols are restorable:
1. **Missing includes/headers** (stdlib functions like `printf`, `open`) - NOT restorable via git
2. **Missing project functions** - Restorable via git history
3. **Declaration/ordering issues** - Need forward declarations

**Implementation:** Maintain lists of known stdlib functions/constants and filter them out before creating repair clues

### Compiler Quirks
- **GCC uses Unicode smart quotes** (', ') not ASCII quotes (') in error messages
- Must match both in regex: `['\u2018]([^'\u2019]+)['\u2019]`

### Content-Based > Name-Based Matching
**Failed Approach:** Match undefined symbols to filenames using patterns like `ts_<filename>_<function>`

**Correct Approach:** Search deleted file contents for symbols using `git show`:
```python
for c_file in deleted_c_files:
    contents = git_show(c_file)
    score = sum(1 for symbol in undefined_symbols if symbol in contents)
    # Restore files with highest scores first
```

## Pipeline Improvements & Detectors

### Detector Architecture Evolution
**Major Refactoring (2025-11-30):** Eliminated all method overrides in detectors

**Before:**
```python
class MyDetector(Detector):
    PATTERNS = {...}
    def pattern_to_clue(self, pattern_name, match, combined):
        # Complex extraction logic
```

**After:**
```python
class MyDetector(Detector):
    PATTERNS = {
        "error_type": r"(?P<file_path>...) (?P<symbol>...)"
    }
    EXAMPLES = [...]
    # No method overrides - base class handles everything via named groups
```

**Benefits:**
- Detectors are now pure data (patterns + examples)
- Consistent approach across all detectors
- Self-documenting via EXAMPLES
- Easier to add new detectors

### Validation Layers (Defense in Depth)
The system now has 3 layers preventing infinite loops:

1. **Planner Validation:** Checks if file exists and matches git before creating plan
2. **Executor Validation:** Validates plan before execution (file exists in git)
3. **Executor Post-Check:** Verifies restoration created actual changes

### Key Detectors Added
- **MakeMissingTargetDetector** - "No rule to make target" errors
- **MakeGlobPatternErrorDetector** - Directory/glob pattern errors
- **CLinkerErrorDetector** - Undefined symbols, missing libraries
- **FopenNoSuchFileDetector** - Multiple patterns for fopen errors
- **TestFailureDetector** - C assertion failures with test file analysis
- **PythonNameErrorDetector** - Python NameError exceptions
- **MissingPythonCodeDetector** - Missing classes/functions/imports

## Error Patterns & Detection

### Common Error Pattern Categories

| Pattern | Example | Detector Type |
|---------|---------|--------------|
| Missing file | `fatal error: file.h: No such file` | File errors |
| Undefined symbols | `undefined reference to 'symbol'` | Linker errors |
| Python errors | `NameError: name 'x' is not defined` | Python code |
| Make errors | `No rule to make target 'x'` | Make errors |
| Permission | `Permission denied: './script.sh'` | Permission errors |
| Test failures | `Assertion failed at line 42` | Test failures |

### Detection Strategy Patterns
1. **Direct pattern matching** - Explicit filename in error
2. **Inference from context** - Extract from surrounding text
3. **Test file analysis** - Read test code to find required files
4. **Build script analysis** - Parse build.rs/Makefile for file operations

## Key Technical Decisions

### Priority Guidelines
- **0**: Critical - missing files blocking execution
- **1**: High - wrong permissions, missing executables
- **2**: Medium - missing Python symbols
- **3**: Low - missing imports
- **4+**: Very low - optional features

### Handler Ordering
Specific handlers before generic ones:
1. Specific build system errors (cargo, make)
2. Compilation errors (C, Rust)
3. Linking errors
4. File access errors
5. Runtime errors
6. Generic catch-alls last

### Git Operations Best Practices
- Use `git show` to read deleted file contents (don't checkout + read + reset)
- Cache `get_deleted_files()` result
- Use `restore_missing_file()` consistently
- Avoid git commands with `-i` flag (interactive not supported)
